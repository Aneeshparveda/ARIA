01 — Project Overview

What is ARIA?

ARIA is a two-unit wireless safety system designed to detect fires, hazardous gas leaks, and dangerous temperature conditions in a room, then respond automatically — sounding alarms, activating a ventilation fan, playing voice alerts, and sending instant messages to a phone via Telegram.

The system is split into a Transmitter (the brain, built on an ESP32 microcontroller) and a Receiver (the actuator, built on an Arduino Uno). These two units communicate with each other using a custom wireless protocol that transmits data using a laser beam and a light sensor — a technology known as Li-Fi.

Rather than relying on a single sensor that could give false alarms, ARIA uses four independent sensing channels simultaneously and combines their readings into a confidence score. The more sensors that agree there is a problem, the more certain the system is — and the more urgently it responds.

The Transmitter is always connected to the internet and hosts a live web dashboard. It monitors the environment continuously, classifies the threat level, and communicates that classification to both the Receiver (via laser) and the user (via Telegram). The Receiver acts purely on what the laser tells it — activating a fan relay, playing pre-recorded audio alerts, and displaying status on its own output indicators.

Why two separate units?

Having a separate actuator unit (the Receiver) means the fan and audio alerts can be placed in a different physical location — for example, the Transmitter sits in the living room monitoring the air, while the Receiver sits near a window to control the exhaust fan. The laser link also means the actuator doesn't need WiFi of its own.

Both MQ-135 and MQ-2 provide two separate outputs: a Digital Output (DO) that gives a simple HIGH/LOW threshold trigger set by a potentiometer on the sensor board, and an Analog Output (AO) that gives a raw voltage proportional to gas concentration. 03 — Sensing & Intelligence

How the System Reads the Room

ARIA doesn't just check if a number exceeds a fixed threshold. It learns the baseline conditions of the specific room it is installed in, then looks for significant deviations from that learned normal — making it far more reliable than a simple trip-wire detector.

The Calibration Phase

When powered on, ARIA enters a three-minute calibration routine before it begins active monitoring. The first 60 seconds are a warm-up period for the MQ gas sensors, which need time for their internal heating elements to reach operating temperature. During the following two minutes, the system samples all sensors repeatedly and calculates average values for temperature, humidity, MQ-135, and MQ-2. These become the personal baseline for this installation.

This means a unit installed in a professional kitchen — where baseline gas and temperature readings are naturally higher — will not constantly false-alarm just because there is cooking happening. It looks for anomalous changes from its own normal, not a generic factory threshold.

Important — Calibration Environment

Calibration must be performed in clean air. If calibration happens during a gas leak or a fire, the dangerous condition would be incorrectly learned as "normal" and would never trigger an alarm. The LCD displays a prompt instructing the user to ensure clean air before calibration begins.

The Four Sensing Channels

🌡️

Temperature & Humidity — DHT22

Measures ambient temperature with ±0.5°C accuracy. A temperature reading above 40°C triggers a Caution state. The baseline also updates slowly during normal conditions, tracking long-term room temperature changes (day/night cycles, seasons) through a technique called exponential smoothing.

🔥

Flame Detection — Infrared Sensor

An infrared-sensitive photodiode detects the specific wavelengths emitted by open flames. It is wired as active-low, meaning it pulls its output pin LOW when flame is present. Due to the extreme urgency of a detected flame, it bypasses the confidence scoring system and immediately triggers a full Emergency state.

💨

Air Quality — MQ-135

Sensitive to CO₂, ammonia, benzene, and general volatile organic compounds. ARIA monitors both the raw analog reading and compares it against the learned baseline. A deviation of 50 units above baseline (or a digital threshold trigger) raises a Caution alert. The readings are also temperature- and humidity-compensated to avoid false positives from weather changes.

🫧

Smoke & Combustible Gas — MQ-2

Detects LPG, propane, butane, methane, smoke, and hydrogen — the gases most associated with fire risk. Like MQ-135, it uses both analog deviation and digital trigger detection. Together, MQ-135 and MQ-2 provide complementary coverage: if you have smoke you might not have high CO₂, and vice versa.

Temperature & Humidity Compensation

Gas sensors are notoriously sensitive to environmental conditions. A hot, humid room will cause the MQ sensors to read higher even if no gas is present. ARIA applies a mathematical compensation formula to every gas reading, adjusting it based on the current temperature and humidity measured by the DHT22. This corrected value is what gets compared to baselines, dramatically reducing weather-related false alarms.

Noise Filtering

Electrical noise on analog lines can cause momentary spikes in sensor readings. ARIA runs each gas sensor reading through an 8-sample rolling average filter — keeping a circular buffer of the last 8 readings and using their mean. This smooths out transient electrical noise while still responding quickly to real gradual changes in air quality.

04 — Wireless Communication

The Li-Fi Laser Link

Li-Fi (Light Fidelity) is the use of visible or infrared light to transmit data — essentially, wireless communication using a beam of light instead of radio waves. ARIA implements its own custom Li-Fi protocol to send status codes from the ESP32's laser module to the Arduino's light sensor.

The system encodes the current threat state into a 5-bit binary packet and transmits it repeatedly, approximately once every 1.5 seconds. Each transmission is a carefully timed sequence of the laser being switched on and off.

The 5-Bit Packet Structure

Each transmission carries a 5-bit frame: 4 data bits carrying the status code, plus 1 parity bit appended at the end for error detection. The parity bit is calculated so that the total number of 1-bits in the full 5-bit frame is always even — if the Receiver counts an odd number of 1-bits, it knows the transmission was corrupted and discards it.

The transmission always begins with a 200ms start pulse — the laser held continuously ON — which the Receiver uses to synchronise its internal clock. After the start pulse, each of the 5 data bits occupies a 100ms window: laser ON means binary 1, laser OFF means binary 0. The complete transmission takes 700ms, leaving 800ms of silence before the next cycle begins.

A Key Engineering Challenge — The Missing Edge

A subtle but critical problem had to be solved in version 4.0.7 of the Receiver firmware. When decoding the laser signal, the obvious approach is to wait for the laser to turn off at the end of the start pulse (a "falling edge") and use that as the synchronisation point. But this fails when the very first data bit after the start pulse happens to be a binary 1 — because the laser was already ON for the start pulse and simply stays on into the first data bit. There is no falling edge to detect.

The fix was to reference all timing from the rising edge at the beginning of the start pulse instead. Since the start pulse is always exactly 200ms, every subsequent bit boundary can be calculated by adding fixed offsets to that initial rising edge timestamp, regardless of whether the laser is on or off at any given transition point.

Why use Li-Fi instead of RF / Bluetooth?

Radio frequency modules (like nRF24L01 or HC-05 Bluetooth) add cost and complexity. A laser module and a cheap LDR resistor together cost almost nothing. The laser beam is also highly directional, meaning it won't interfere with or be confused by other wireless devices in the area. It is a uniquely elegant low-cost solution for a fixed-installation two-unit system.

05 — Threat Classification

How Danger Is Assessed

Every two seconds, the system re-evaluates all sensor readings and classifies the current environment into one of three threat levels. The classification follows a strict priority hierarchy.

Level 0

Normal

All sensors within their learned baseline ranges. Green LED on. System transmits heartbeat codes via laser. Baseline values continue to update slowly.

Level 1

Caution

One or more sensors elevated but no immediate fire detected. Yellow LED on, buzzer pulses slowly. Baseline updates are frozen to prevent the elevated reading from being absorbed as "normal."

Level 2

Emergency

Flame detected, or Manual Emergency button pressed. Red LED strobes rapidly, buzzer sounds continuously at high frequency. Fan relay activates at Receiver. Telegram SOS sent immediately.

The Confidence Score

During a Caution state, the system calculates a confidence score from 1 to 4 representing how many of the four independent sensors are simultaneously indicating a problem. A score of 1 might be a simple cooking smell triggering MQ-135 briefly. A score of 3 — with temperature, MQ-135, and MQ-2 all elevated together — strongly suggests a real developing fire situation. This score is displayed on the LCD, sent in the Telegram alert, and shown on the web dashboard, giving the user meaningful context rather than just a binary alarm.

Baseline Freezing

One of ARIA's more subtle but important behaviours is that the adaptive baselines only update when the system is in a Normal state. The moment a Caution is triggered, baseline learning is paused. This prevents the system from "adapting away" a real slow-developing gas leak — if it kept updating the baseline during an elevated condition, the leak would gradually become invisible to the detector.

Caution Timeout

The system also tracks how long a Caution condition has been active. If sensors remain elevated for an extended period, this is treated as a sustained risk rather than a transient spike, and the Telegram alert system can issue renewed notifications on a cooldown timer to ensure the user is not left unaware of a persisting problem.

The Manual Override Buttons

Two physical buttons give authorised personnel direct control over the system. The Emergency Button instantly forces the system into a full Emergency state — useful if a person sees or smells fire before the sensors react. The Reset Button requires a deliberate three-second hold (shown with a countdown on the LCD) to prevent accidental resets, after which the system returns to Normal and sends an "All Clear" Telegram message confirming authorised reset.

06 — The Receiver Unit

Actuation & Response

While the Transmitter is responsible for all the intelligence, the Receiver is responsible for all the physical responses at its location. It operates entirely independently of the internet — its only input is the laser beam from the Transmitter, and its outputs are the relay, speaker, and serial debug log.

How the Receiver Decodes the Laser

STEP 01

Polarity Auto-Detection

On startup, the Receiver samples the LDR 20 times and determines whether the sensor outputs HIGH or LOW when dark (no laser). This lets the firmware adapt automatically regardless of whether the LDR module has an active-high or active-low output — no manual configuration needed.

STEP 02

Rising Edge Detection

The main loop runs continuously, watching for the laser to switch from OFF to ON. This rising edge marks the beginning of a transmission and starts an internal timer. This timer is the reference clock for the entire packet decode.

STEP 03

Start Pulse Validation

At 150ms after the rising edge, the Receiver checks if the laser is still on. If yes, this confirms it is a genuine 200ms start pulse and not a stray noise spike. If the laser has already gone off, the event is discarded as a timing error and the system returns to waiting.

STEP 04

Bit Sampling

Each of the 5 data bits is sampled at its midpoint — 50ms into its 100ms window, counting from the rising edge. Bit 4 is sampled at 250ms, Bit 3 at 350ms, and so on down to Bit 0 at 650ms. Sampling at the midpoint of each window avoids the uncertainty of the transition edges.

STEP 05

Parity Check

The 5 received bits are checked using even parity. If the XOR of all 5 bits equals zero, the frame is clean. If not, the frame is flagged as a parity failure and discarded. The error counters are incremented and the decode cycle resets, waiting for the next transmission.

STEP 06

Action Execution

If the frame passes parity, the 4-bit code is extracted from bits 4:1 and matched to a known command (Heartbeat, Warning, Emergency, All Clear). The appropriate physical response is then triggered.

The Relay & Fan Control

One of the most important safety features in the Receiver is the confirmation counter for the relay. When an Emergency code arrives, the relay does not activate immediately on the first packet — it requires three consecutive Emergency packets before switching the fan on. This prevents a single corrupted or misread transmission from accidentally activating the relay. Since the Transmitter sends a new packet every 1.5 seconds, the relay activates after roughly 4.5 seconds of sustained emergency signals — fast enough for a real emergency, but immune to single-packet errors.

The relay is also protected by a safety watchdog — a periodic check that ensures the relay cannot remain ON if the system has returned to Normal state. If this contradiction is ever detected, the relay is forced off immediately.

Link Loss Detection

If the Receiver stops receiving any valid packets for more than 15 seconds — perhaps because the laser is physically blocked, or the Transmitter has lost power — it declares a link lost condition, forces the relay off as a safety precaution, and returns to Normal threat level. When transmissions resume, it automatically declares link restored and resumes normal operation.

Audio Alerts — DFPlayer Mini

The Receiver contains a DFPlayer Mini module, a small self-contained MP3 player that reads audio files from a microSD card. Four pre-recorded audio tracks correspond to the four system states: a startup jingle, a warning announcement, an emergency alarm, and an all-clear message. These play through a connected speaker whenever the threat state changes. During sustained emergencies, the emergency audio repeats every 30 seconds; during Caution, the warning repeats every 60 seconds.

07 — Remote Alerting

Telegram Bot Integration

The ESP32 Transmitter connects to a Telegram Bot and can send formatted status messages directly to a designated group chat or personal account. This means the homeowner receives an alert on their phone regardless of where they are in the world, as long as they have internet access.

Messages are sent over HTTPS using Telegram's standard Bot API. The ESP32 maintains a dedicated background task — running on the second processor core — purely for handling Telegram sends. This ensures the main sensor monitoring loop is never delayed by network operations.

Alert Types

The system sends five distinct types of Telegram messages: an Emergency Alert when fire or critical conditions are detected, a Caution Alert when readings are elevated but not critical (including which specific sensors triggered and by how much), an All Clear message when conditions normalise, a Manual Emergency SOS when someone physically presses the emergency button, and a periodic Heartbeat every five minutes confirming the system is alive and online, with a summary of current readings.

The Cooldown System

To prevent a rapidly fluctuating sensor from flooding the Telegram chat with dozens of messages per minute, a 60-second cooldown is enforced between successive Telegram sends. Messages are queued in a first-in first-out buffer, and if the queue overflows during the cooldown, new messages are gracefully dropped rather than crashing the system.

A Low-Level Bug Fix — Memory Safety

A critical memory corruption bug was fixed in version 4.0.4. The previous implementation tried to pass C++ String objects through FreeRTOS queue slots. FreeRTOS copies queue items using raw memory copy, which does not understand C++ object ownership — the result was the String's internal text buffer being freed prematurely, leading to heap corruption and random crashes. The fix was to pass only a plain pointer to a freshly heap-allocated C-string through the queue, with the receiver task responsible for freeing the memory after sending. This is a fundamental principle of safe concurrent programming: never share complex C++ objects across thread boundaries by value.

08 — Web Dashboard & Weather

Live Local Interface

The ESP32 hosts a web server on the local WiFi network. Any device on the same network — phone, tablet, laptop — can open the dashboard in a browser by navigating to the ESP32's IP address. The page auto-refreshes every 10 seconds and polls for live sensor data every 2 seconds via a JSON endpoint.

The dashboard shows the current threat state (with a pulsing red animation during emergencies), a live table of all sensor readings, the current confidence score with active sensor list, the Li-Fi code being transmitted, an event log of the last 10 state changes with timestamps, and a 5-hour local weather forecast.

The Weather Forecast

ARIA integrates with the Open-Meteo API, a free weather service requiring no API key. Using the GPS coordinates configured in the firmware, it fetches a 5-hour forecast including temperature, humidity, and weather condition codes for the local area. The forecast refreshes every 30 minutes.

The weather data is contextually useful for interpreting sensor readings — if outdoor humidity has suddenly spiked due to rain, and the indoor MQ sensors have slightly elevated readings, the dashboard lets the user quickly correlate the two and assess whether the elevated readings are environmental noise or a genuine concern.

WiFi Reconnection

The system scans for WiFi networks matching two known hotspot keywords (allowing it to connect to either a home router or a phone hotspot). If connectivity is lost, it automatically reattempts connection every 15 seconds. The web server and Telegram functionality are gracefully suspended during offline periods and restored when connection is re-established. Core sensor monitoring and Li-Fi communication continue uninterrupted regardless of WiFi state.

09 — Reliability & Safety Design

Built to Not Fail

A safety system that crashes during an emergency is worse than no system at all. ARIA incorporates multiple layers of defensive design specifically to ensure it remains operational under adverse conditions.

Multi-Core Task Separation (ESP32)

The ESP32 has two processor cores. ARIA deliberately pins the Telegram sending task to Core 0 while all sensor reading, threat analysis, Li-Fi transmission, and web server handling run on Core 1. This means even if a Telegram send stalls waiting for a slow network response, the sensor monitoring loop never pauses. The laser continues transmitting and the alarms continue functioning completely independently of internet activity.

Sensor Validation

Every reading from every sensor is validated before use. DHT22 readings are checked for the valid temperature range (−40°C to 85°C) and for NaN values (which indicate a failed read). ADC values are checked for the valid 12-bit range (0–4095). If a sensor read fails, the system flags the sensor as invalid and continues operating with the remaining sensors rather than crashing or giving misleading data.

The Watchdog on the Receiver

The Arduino Uno's hardware watchdog timer is explicitly disabled in the Receiver firmware. This may seem counterintuitive for a safety device, but it is intentional: the Li-Fi decoder runs a tight polling loop that must never be interrupted. The hardware watchdog, if enabled, would reset the microcontroller if the main loop ever took too long — which could happen legitimately during certain timing-critical decoding sequences. The Link Loss Detection mechanism serves as the Receiver's watchdog instead: if the Transmitter fails, the Receiver detects link loss and fails safe.

Relay Safety Watchdog

A dedicated watchdog function runs on the Receiver every 10 seconds. It checks one specific condition: if the threat level is currently Normal, the relay must be off. If this invariant is ever violated — due to any possible software bug or unexpected state transition — the relay is immediately and unconditionally forced off. A fan running when it shouldn't is a minor inconvenience. A fan not running during a fire is a disaster. The safety watchdog ensures the bias always falls toward the safe side.

Heap Memory Monitoring

The ESP32 firmware periodically logs the free heap memory and the historical minimum free heap to the serial debug output. This allows the developer to detect memory leaks over long runtimes — if the free heap is slowly decreasing over hours of operation, that indicates a memory management problem that would eventually crash the system. By monitoring this in development, any such leaks can be caught and fixed before deployment.

Statistics & Diagnostics

The Receiver maintains a comprehensive set of runtime counters: total messages received, good frames decoded, parity failures, timing errors, start pulse detections, and total error count. These are printed to the serial monitor every 5 minutes in a formatted status report. This diagnostic data allows the developer or installer to assess the quality of the Li-Fi link over time — if parity failures are high, it suggests the laser needs physical realignment, or the LDR threshold potentiometer needs adjustment.
