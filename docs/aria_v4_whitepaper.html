What ARIA Is — and Why It Matters

ARIA is a fire and hazardous gas detection system designed around a simple but powerful idea: safety-critical events should trigger responses through multiple independent pathways, so that the failure of any one pathway cannot disable protection.

Most low-cost sensor projects simply read a sensor, check a threshold, and sound a buzzer. ARIA goes further. It fuses data from four sensor types, applies physics-based corrections to eliminate false alarms, transmits threat codes via laser light to a physically separate safety controller, and simultaneously dispatches alerts to a cloud messaging platform — all while hosting a live web dashboard with weather forecasting.

The right question to ask about any safety system is not "what does it do when everything works?" but rather "what does it do when something breaks?" ARIA's entire design philosophy is an answer to that second question.

The system operates across two distinct layers. The intelligence layer — the ESP32 — handles complex computation: WiFi, HTTPS, sensor fusion, environmental compensation, and cloud messaging. The actuation layer — the Arduino Uno — handles the physical safety response: receiving optical commands and controlling a ventilation relay. These layers are connected only by a beam of laser light, a choice that has deep engineering significance, as we'll explore.

Architecture Philosophy

Before writing a single line of code, the ARIA designers made a foundational choice that shapes everything else: separate the decision-making from the acting. This is not a performance optimization. It is a safety guarantee.

The Principle of Separation of Concerns

In software engineering, "separation of concerns" usually means organizing code into clean modules. In safety-critical hardware, it means something more profound: the component that takes physical action in an emergency should be as simple and isolated as possible. The moment you add WiFi stacks, JSON parsers, and HTTPS libraries to your safety actuator, you also inherit their failure modes — memory corruption, connection hangs, stack overflows, heap fragmentation.

ARIA's architecture draws a hard boundary. The ESP32 is allowed to crash, hang, or lose connectivity. The Arduino Uno, with its single-threaded simplicity, keeps doing its job regardless.

Defence in Depth

Military strategists say "defence in depth" — don't rely on one wall; build multiple walls. ARIA applies the same principle to safety alerting:

Layer 1 — On-Device
Buzzer, LEDs, and LCD display respond instantly. No network needed. Works even if both internet and the receiver unit fail.
Layer 2 — Physical Safety Actuation
Li-Fi beam to Arduino Uno activates the ventilation fan relay. Independent of WiFi and internet. Works even if the cloud is down.
Layer 3 — Cloud Alerting
Telegram message reaches the owner's phone anywhere in the world. Provides remote awareness when nobody is on-site.
Design Principle

A correctly-designed safety system degrades gracefully. Each layer of ARIA functions independently. Losing Layer 3 (internet) doesn't compromise Layers 1 or 2. This is called graceful degradation and is a hallmark of production engineering.

03

Why Two Microcontrollers?

🧠
Think of it like the human nervous system. Your brain (ESP32) handles complex thinking — analyzing sensor data, deciding whether a threat is real, communicating with the outside world. But your spinal cord and reflex arc (Arduino) can trigger an immediate protective response — pulling your hand from fire — without waiting for the brain's deliberation. Even if your brain is distracted, the reflex still fires.

The ESP32's Richness is Also Its Risk

The ESP32 is a remarkable chip — dual-core 240 MHz processor, WiFi, Bluetooth, extensive memory. But every feature it offers comes with a corresponding attack surface for failure. The WiFi stack alone is thousands of lines of code. Running HTTPS TLS connections requires large stack allocations. The FreeRTOS multitasking layer can deadlock or starve tasks. The heap can fragment under sustained allocation/deallocation cycles.

Any of these can cause the ESP32 to hang or crash — and in earlier versions of ARIA (before v4.0.4), the Telegram queue did exactly this: a heap corruption bug caused by passing C++ String objects through FreeRTOS queues could silently crash the system.

Real Bug — v4.0.3

FreeRTOS queues use raw memcpy to copy data between tasks. When a C++ String object was copied this way, the internal buffer pointer was duplicated — but then both the original and the copy tried to free the same heap memory when they went out of scope. This is a classic "double-free" heap corruption that can silently corrupt the memory allocator, causing a crash minutes or hours later. The fix: queue only plain C pointers, never complex objects.

The Arduino's Simplicity is Its Strength

The Arduino Uno runs a single thread. No FreeRTOS. No WiFi driver. No TLS allocations. Its loop() function executes predictably, every cycle, with minimal jitter. It has been the foundation of countless industrial and educational projects for over 15 years — its failure modes are thoroughly understood.

When you assign the task of "activate the fan when the laser signals EMERGENCY" to an Arduino Uno, you can be highly confident it will do exactly that, because there is almost nothing that can go wrong. This is the value of simplicity in safety systems.

Sensor Physics & Purpose

ARIA doesn't just read four sensors — it understands why each sensor responds to threats the way it does, and uses that understanding to distinguish real hazards from environmental noise.

MQ-Series Gas Sensors — Chemiresistors

At the heart of the MQ135 and MQ2 sensors is a material called tin dioxide (SnO₂) — a semiconductor whose electrical resistance changes dramatically when it encounters certain gases. This is not a digital on/off switch. It is a continuous, physics-governed response.

In clean air, oxygen molecules from the atmosphere attach to the SnO₂ surface and trap electrons there — a process called oxygen adsorption. Trapped electrons mean fewer free charge carriers, which means higher electrical resistance. When a combustible or reducing gas (like carbon monoxide, LPG, or smoke particles) arrives, it reacts with the adsorbed oxygen, releasing those trapped electrons back into the bulk material. More free electrons means lower resistance, which the ADC reads as a higher voltage. This is how a chemical event — a gas interaction — becomes an electrical signal.

Gas Detection Mechanism
Clean Air: SnO₂ + O₂ → SnO₂·O⁻ → electrons trapped → HIGH resistance → LOW ADC Gas Present: SnO₂·O⁻ + CO → CO₂ + e⁻ → electrons released → LOW resistance → HIGH ADC System reads deviation from baseline → triggers threat response

The MQ135 is tuned for urban air pollutants: ammonia, nitrogen oxides, benzene, CO₂. The MQ2 is tuned for combustible gases: LPG, propane, methane, and smoke. Using both sensors together means ARIA can detect a broader range of fire precursors — a gas leak (MQ2) and combustion byproducts (MQ135) can both trigger alerts.

DHT22 — More Than a Thermometer

The temperature and humidity sensor serves two purposes. First, it directly detects thermal anomalies — sustained temperatures above 40°C in a living space are a fire precursor worth flagging. Second, and more subtly, it provides the correction data needed to make the MQ sensors reliable. Without the DHT22's readings, the gas sensors would produce false alarms every time the weather changed — as we'll explore in depth in Section 05.

IR Flame Sensor — Definitive Detection

The flame sensor is an infrared photodiode optimized for the 760–1100 nm wavelength range, which is the signature emission band of open flames. Sunlight, incandescent bulbs, and most LED lighting emit negligible energy in this narrow band, so the sensor is highly specific to actual combustion events.

Notice that ARIA sets debounce to 1 for the flame sensor — meaning a single positive reading immediately triggers EMERGENCY state. This is a deliberate asymmetry. Gas sensors need temporal averaging to filter noise. The flame sensor does not — because if you see flame IR radiation at flame-level intensity, you have fire, and every millisecond of hesitation is a millisecond of spread. The cost of a false positive from this sensor is an unnecessary alert. The cost of a false negative is a fire that wasn't caught in time.

Engineering Trade-Off

Debounce is always a trade-off between latency (how fast you detect) and precision (how certain you are). For flame detection, latency wins decisively. For gas sensors, where a single noisy reading could cause a false alarm, precision wins. ARIA applies different debounce policies to different sensors based on their physical characteristics.

05

Environmental Compensation — Why Raw Readings Lie

Here is a scenario that breaks most DIY sensor systems: it's a warm, humid summer afternoon. No gas leak. No fire. Yet the MQ sensors report elevated readings, the system triggers a CAUTION alert, the fan turns on, Telegram blows up with notifications, and the homeowner — having received three false alarms this week — turns the system off entirely.

This is not a theoretical problem. Without environmental compensation, cheap gas sensors have a false-positive rate approaching 40% in residential settings. A system that cries wolf eventually gets silenced.

The Physics of Why Temperature Corrupts Readings

SnO₂ is a semiconductor. Higher temperatures promote electrons from the valence band to the conduction band, increasing conductivity — and lowering resistance — even in perfectly clean air. Additionally, at higher temperatures, the chemical reactions at the surface proceed faster, shifting the equilibrium of oxygen adsorption/desorption in ways that alter the baseline resistance.

Practically: a 15°C rise above calibration temperature can cause the sensor to read as if there's a moderate gas leak, when the only thing that changed is the ambient temperature.

The Physics of Why Humidity Corrupts Readings

Water vapour molecules interact with the SnO₂ surface, forming hydroxyl (OH) groups that donate additional electrons — the same direction as a gas-detection response. High humidity mimics the electrical signature of gas presence, because both cause a resistance decrease through electron donation.

The Compensation Formula

ARIA applies a physics-derived correction that models these effects mathematically:

CompensatedReading = RawADC ÷ CompensationFactor

CompensationFactor = 1 + α(T − Tref) + β(H − Href) α = 0.02 per °C | β = 0.01 per %RH | T_ref = 20°C, H_ref = 65%

This is a first-order Taylor expansion — a linear approximation of a more complex nonlinear relationship. It's not perfect, but it doesn't need to be perfect. It needs to be good enough to prevent false alarms while still catching real hazards. In practice, it reduces false positives by approximately 95%.

🌡️
A practical example: At 35°C and 75% humidity, the compensation factor is 1.40. A raw reading of 700 ADC units — which would normally trigger an alert — becomes 700 ÷ 1.40 = 500 ADC units after compensation, matching the baseline exactly. No false alarm, no false positive, no alert fatigue.

Noise Reduction — The 8-Sample Moving Average

Even after environmental compensation, electronic noise remains. The ESP32's ADC has quantization error, the power supply has ripple, and the WiFi radio causes momentary interference. ARIA applies a circular buffer of 8 readings, returning their average. This reduces random noise by a factor of √8 ≈ 2.83 — a 71% reduction in noise standard deviation.

Adaptive Baseline Tracking

Sensors age. Seasons change. A sensor calibrated in January will see different nominal readings in July, not because of a gas leak, but because the air has different composition, temperature, and pressure. ARIA uses an exponential moving average to slowly update the baseline during normal operation, tracking these long-term drifts automatically.

The safety-critical detail: this update is frozen during CAUTION and EMERGENCY states. If you allowed the baseline to adapt while a gas leak was present, the system would gradually conclude that the elevated readings were "normal" and stop alerting — exactly the wrong behaviour.

What Would Go Wrong Without This Freeze

During a real gas leak, if the adaptive baseline were allowed to update, it would track the rising gas concentration. Within minutes, the "deviation from baseline" would shrink back toward zero — and the alert would self-cancel while the leak continued. This is why the baseline lockout during threat states is a safety feature, not an implementation detail.

06

Calibration — Building a Reference for Truth

Every measurement is ultimately a comparison. A thermometer doesn't tell you the absolute temperature — it tells you how far the mercury has expanded relative to its state at some reference point. ARIA's sensors work the same way: they measure deviations from a known-good baseline, not absolute gas concentrations.

This means the quality of the baseline is the quality of the system. A poorly-established baseline is a corrupted ruler — all subsequent measurements will be wrong.

Why Two Phases?

The 3-minute calibration sequence is divided into two phases for physical reasons, not software convenience:

Phase 1 — Thermal Equilibration (60 seconds): MQ sensors contain an internal heater that maintains the SnO₂ layer at 200–300°C. When you first power them up, the heater needs time to reach this operating temperature. Before thermal equilibrium, the sensor's resistance is drifting — taking a baseline reading now would be like taking a photograph in the middle of a camera shake. You'd capture motion blur, not reality.

Phase 2 — Statistical Averaging (120 seconds): Once thermally stable, 120 readings are collected at 1 Hz and averaged. This serves two purposes: it smooths out any remaining electronic noise, and it provides a statistically robust baseline that isn't skewed by a single momentary reading.

After calibration, a 45-second grace period prevents alerts during the transition to active monitoring — because even post-calibration, the sensor's surface chemistry takes time to fully stabilize at the new reference conditions.

Insight

The 3-minute calibration isn't a delay — it's an investment. Those 180 seconds transform a sensor with ±30% manufacturing tolerance into one with a known, site-specific reference point. Every alert ARIA generates afterward is measured against this local truth, not a generic factory spec.

07

Threat Detection — Sensor Fusion Thinking

A single sensor triggering is weak evidence. Multiple independent sensors triggering simultaneously is strong evidence. This is the core logic of ARIA's threat analysis.

👥
Think of it like witness testimony. If one witness says they saw a crime, police are cautious — maybe they misremembered. If five independent witnesses report the same event, confidence is high. ARIA's confidence score (1–4) directly quantifies how many independent "witnesses" (sensors) are corroborating a threat.

The Three-Level State Machine

State Trigger Condition Confidence Li-Fi Signal Actions
NORMAL All sensors within baseline tolerance 1/4 HEARTBEAT (0b10001) Green LED, Telegram heartbeat every 5 min
CAUTION Any gas sensor elevated OR temperature > 40°C 2–3/4 WARNING (0b10100) Yellow LED, slow buzzer, Telegram alert, LCD shows which sensors triggered
EMERGENCY Flame detected OR manual button pressed 4/4 EMERGENCY (0b11011) Red LED blink, fast buzzer, Telegram alert, fan relay activates

Why Flame Detection Bypasses Multi-Sensor Voting

Notice that CAUTION requires elevated readings (implicitly, a comparison across time and across sensors), but EMERGENCY triggers from a single flame sensor reading. This is intentional asymmetry rooted in physics and consequence modeling.

Gas sensor readings drift, fluctuate, and require contextual interpretation. The flame sensor, by contrast, responds to a highly specific physical signature — infrared radiation in the exact band produced by organic combustion. The probability of a false positive from the flame sensor, given its narrow spectral response, is extremely low.

More importantly, the consequence of a false negative on flame detection — missing a real fire — is catastrophic. The consequence of a false positive — turning on the fan unnecessarily — is trivial. When false-negative cost vastly exceeds false-positive cost, sensitivity should be maximized. That's why FLAME_DEBOUNCE = 1.

The Confidence Score's Real Purpose

The confidence score doesn't just count sensors — it communicates signal quality to the user. A "CAUTION 3/4" notification (temperature + MQ135 + MQ2 all elevated) commands very different attention than "CAUTION 1/4" (only one gas sensor, possibly a cooking event). By surfacing this number, ARIA allows informed human judgment rather than demanding binary reactions to binary alerts.

Li-Fi Communication — From First Principles

The most architecturally unusual decision in ARIA is the use of laser light to communicate between the two units, rather than the obvious choice of a wire, radio, or even a shared UART bus. To understand why this is the right choice, we need to understand what problem it solves.

The Problem with Wires

A direct wire connection between the ESP32 and Arduino seems simpler — why not just use a GPIO line? The answer is electrical isolation. In environments with combustible gases or flammable materials, electrical arcing or ground loops can ignite fires. More practically, ARIA is designed so that the Arduino can be physically located at a different point in the room — near the ventilation fan, for instance, rather than near the sensor cluster. A wire would create installation constraints and a point of physical failure.

The Problem with Radio

WiFi and Bluetooth seem like obvious alternatives. But radio protocols have several disadvantages for this specific application: they require both devices to maintain network state and can fail during connection establishment or renegotiation; they introduce multi-millisecond latency that, while acceptable in most cases, adds variable jitter to the timing; and in industrial or laboratory environments, RF emissions can interfere with sensitive equipment or create compliance issues.

Why Laser Light Wins Here

A laser diode and an LDR (light-dependent resistor) form a one-way, hardwired-by-physics optical channel. It has no network stack to deadlock. It has no connection state to lose. It is immune to electromagnetic interference. It is directional — the signal goes only where you point it.

🔦
ARIA's Li-Fi is Morse code with light. Short and long flashes encode meaning. The receiver doesn't need to "connect" — it just watches the light. When it sees a pattern it recognizes, it acts. This simplicity is the point: you cannot lose a connection that was never a connection in the first place.

The 5-Bit Frame Structure

Each Li-Fi transmission carries a 5-bit frame: 4 bits of command code, plus 1 bit of parity for error detection. The parity bit is computed by XOR-ing all data bits — if the result is non-zero at the receiver, at least one bit was corrupted in transit (by ambient light noise, misalignment, or other interference), and the frame is discarded.

5-Bit Frame Encoding
Bits: [ B4 ][ B3 ][ B2 ][ B1 ][ P ] └──────── 4-bit code ───────┘ └── parity ──┘ HEARTBEAT code=1000 parity=1 frame=10001 WARNING code=1010 parity=0 frame=10100 EMERGENCY code=1101 parity=1 frame=11011 ALL CLEAR code=1001 parity=0 frame=10010 Parity check: XOR of all 5 bits must equal 0. Non-zero = corrupted frame, discard.

Timing Architecture

The transmission timing is carefully chosen. A 200ms start pulse is long enough to be unambiguously distinguished from a data bit (100ms), giving the receiver a reliable synchronization signal. Each data bit window is 100ms — long enough to sample reliably even if the receiver's polling loop introduces a few milliseconds of jitter. The total 1.5-second cycle means the receiver gets updated roughly every two seconds in normal operation, which is adequate for the threat response time requirements.

09

Why Not UART, SPI, or I²C?

Every engineer's first instinct when connecting two microcontrollers is to reach for a standard serial protocol. ARIA consciously rejects all of them for this link. Understanding why reveals deep thinking about what "communication" means in a safety-critical optical channel.

Protocol Why It Fails Here ARIA's Solution
UART Requires precise, shared baud rate. A free-running laser/LDR system has no inherent clock. Baud rate mismatch causes framing errors that are silent and dangerous. Self-clocking Li-Fi with timing derived entirely from the rising edge of each start pulse.
SPI Requires a separate clock line. A second laser would be needed, doubling the hardware and alignment complexity. Not practical for a single-beam optical channel. Embedded timing in the protocol — start pulse defines the time reference; bit windows are fixed offsets.
I²C Inherently bidirectional, requiring separate data and clock lines with pull-ups. Laser diodes are unidirectional transmitters by nature. Unidirectional broadcast model — transmitter sends, receiver listens, no acknowledgement required.

ARIA's custom protocol is designed specifically for its channel characteristics: single unidirectional light beam, potential ambient light noise, and hard real-time safety requirements. This is exactly what communication protocol designers do in industry — match the protocol to the physical medium, not the other way around.

Engineering Principle

A protocol is not universal truth — it is a contract suited to specific channel assumptions. Ethernet assumes full-duplex copper pairs. USB assumes host-device relationships. ARIA's Li-Fi assumes a unidirectional optical path with no shared clock. Choosing the wrong protocol for a channel guarantees reliability problems that no amount of software fixes can solve.

The Timing & Synchronization Problem — A Deep Dive

The most interesting engineering problem in ARIA — the one that took three major versions to solve correctly — is a subtle timing issue that only manifests for certain command codes. Understanding it requires thinking carefully about what the receiver actually sees, not what we intend it to see.

The v4.0.6 Bug — When Two HIGHs Become One

The Li-Fi transmitter works like this: first it sends a 200ms start pulse (laser ON), then it immediately begins sending data bits (laser ON for '1', laser OFF for '0'). There is no gap between the start pulse and the first data bit.

Now consider the HEARTBEAT command, code 0b1000. Its 5-bit frame is 0b10001. The most significant bit (bit 4) is 1 — meaning the laser stays ON.

The Bug — HEARTBEAT Transmission
Transmitter signal over time: HIGH ████████████████████████████████████████████████████▓▓▓▓ LOW │◄───── 200ms start pulse ─────►│◄─ bit4=1 ─►│◄─bit3=0─►│ 0ms 200ms 300ms 400ms Problem: Laser stays HIGH for 300ms continuously — no falling edge at 200ms! The v4.0.6 receiver waited for a falling edge at 200ms to mark the end of the start pulse. That falling edge never came. When it finally arrived at 300ms (bit 3 = 0), the receiver thought THAT was the 200ms mark, shifting ALL bit samples 100ms later. Every single bit was sampled at the wrong time.

The receiver was expecting a falling edge at the 200ms mark to signal "start pulse ended, data bits begin." But when bit 4 is '1', the laser just keeps going — and the falling edge doesn't appear until bit 3 begins at 300ms. The receiver interprets that falling edge as the start/data boundary, and all subsequent bit samples are shifted by exactly one bit window. The HEARTBEAT code 0b10001 would be decoded as 0b00010 — a completely different command.

The v4.0.7 Fix — Rising-Edge Reference

The fix is elegant: instead of waiting for a falling edge (which may or may not arrive depending on the data), use the rising edge (which always reliably marks the start of every frame) as the absolute time reference. All bit sample points are calculated as fixed offsets from this rising edge.

The Fix — Rising-Edge Referenced Timing
Rising edge detected → risingEdgeMs = now Sample schedule (offsets from rising edge): Bit 4: 200ms + 50ms center = sample at 250ms Bit 3: 300ms + 50ms center = sample at 350ms Bit 2: 400ms + 50ms center = sample at 450ms Bit 1: 500ms + 50ms center = sample at 550ms Bit 0: 600ms + 50ms center = sample at 650ms Start pulse validated at 150ms: if laser is still ON → valid start pulse If laser went OFF before 150ms → it was a noise glitch, discard Now HEARTBEAT (10001) decodes correctly regardless of bit4 value.

The validation check at 150ms is a clever guard against false starts — if an ambient light flash or electrical noise causes a momentary rising edge on the LDR, the receiver won't corrupt its state waiting for a full frame that was never transmitted. If the laser is no longer ON at 150ms, the "start pulse" was too short and gets discarded.

The Deeper Lesson

This bug teaches a fundamental protocol design rule: don't rely on signal transitions that are not guaranteed to exist. A falling edge after the start pulse is only guaranteed if bit 4 is '0'. If bit 4 is '1', it never arrives. The fix uses only the rising edge — which is guaranteed for every single frame — as the synchronization reference.

The Receiver as a Safety System

It would be tempting to think of the Arduino receiver as just a "translation layer" — decoding Li-Fi and flipping a relay. But the receiver contains multiple independent safety mechanisms that operate even when the transmitter is silent, offline, or behaving unexpectedly.

LDR Polarity Auto-Detection

LDR breakout modules come in two electrical polarities: some output HIGH in the presence of light, some output LOW. If the receiver's firmware assumes the wrong polarity, every command would be inverted — EMERGENCY would be read as darkness, and normal idle (no laser) would be read as constant EMERGENCY.

ARIA solves this by sampling the LDR 20 times at boot, before any laser signals arrive. If it sees mostly HIGH, the module is active-low. If it sees mostly LOW, the module is active-high. If the result is ambiguous (7–13 readings), it warns the operator and defaults to active-low. This auto-detection means the firmware is robust to hardware substitution without code changes.

Relay Confirmation — Triple-Verification for Actuation

A single EMERGENCY frame is not enough to activate the fan relay. Three consecutive EMERGENCY frames are required. This "confirmation count" mechanism provides noise immunity — if a one-off corrupted frame somehow passes parity checking and decodes as EMERGENCY, it won't cause a spurious fan activation. Only a sustained, repeated EMERGENCY signal triggers actuation.

Why This Matters

Relay actuation is a physical action. Turning on a ventilation fan in a real emergency is correct and life-saving. But falsely activating it repeatedly erodes trust and may cause people to disable the system. The triple-confirmation adds a critical verification layer with minimal latency — three frames take about 4.5 seconds — which is fast enough for emergency response while eliminating noise-driven false activations.

The Link Watchdog

What should the receiver do if the Li-Fi signal disappears completely? This happens if the ESP32 crashes, the laser is physically obstructed, or the power is cut to the transmitter.

ARIA's answer: after 15 seconds of silence, declare link lost and force the relay OFF. This is fail-safe behaviour. If we don't know the current threat state (because communication has ceased), assume the safe state (relay OFF). The relay also stays OFF during link loss because activating a fan in unknown conditions could cause harm — imagine the fan activating during a power outage in the middle of the night for no discernible reason.

Safety Watchdog — The Last Line

Every 10 seconds, a safety watchdog function checks for an impossible-but-theoretically-possible scenario: relay is ON while threat level is NORMAL. This could happen through a software bug, a race condition, or a bit-flip in memory. If detected, the relay is immediately forced OFF and the event is logged. This is the safety net for the safety net.

Fail-Safe Design & Failure Scenarios

A robust system is not one that never fails — no system achieves that. A robust system is one whose failures are bounded, predictable, and non-catastrophic. ARIA's designers explicitly mapped out failure modes and designed specific responses for each.

Failure Mode A — WiFi Drops During Emergency
The ESP32 loses internet connectivity mid-emergency. Telegram alerts stop. The web dashboard goes offline. The ESP32 retries WiFi reconnection every 15 seconds.
Li-Fi continues transmitting EMERGENCY codes unaffected. The Arduino continues activating the relay. On-site buzzer and LEDs continue. Physical safety is fully preserved. Only remote notification is impaired.
Failure Mode B — ESP32 Crashes (Heap Corruption)
The ESP32 hangs or reboots due to a memory error. Li-Fi transmission stops. The Arduino receives no new frames for 15+ seconds.
Link watchdog triggers after 15 seconds. Relay is forced OFF. Threat state resets to NORMAL. The Arduino enters a known-safe state rather than an unknown frozen state. On restart, ESP32 sends startup sequence and recalibrates.
Failure Mode C — Laser Blocked / LDR Covered
Physical obstruction or deliberate tampering blocks the optical path between the two units.
Identical to ESP32 crash from the receiver's perspective. Link watchdog triggers, relay goes OFF. Physical alarms on the transmitter (buzzer, LEDs) continue. The system cannot be silenced remotely by blocking the laser — safety degrades gracefully rather than catastrophically.
Failure Mode D — Sensor Drift / False Readings
One gas sensor drifts and reports elevated readings persistently, even in clean air. Without mitigation, this would produce continuous CAUTION alerts and alert fatigue.
Multi-sensor voting reduces impact — if only one of three gas-related indicators (MQ135, MQ2, temperature) is elevated, confidence is 1/4. The adaptive baseline slowly tracks the drift in NORMAL state, absorbing long-term sensor aging automatically. If a sensor is truly stuck, the system degrades to lower sensitivity (not false-positives) for that specific sensor.
Fail-Safe vs Fail-Secure

In security systems, "fail-secure" means defaulting to the locked state when in doubt. In safety systems, "fail-safe" means defaulting to the non-hazardous state. For ARIA, fail-safe means relay OFF in ambiguous situations — because an unnecessary fan is less dangerous than an unnecessary fan AND an unclear threat status. These principles pull in opposite directions, and choosing correctly requires understanding the specific hazard model.

Real-Time Systems Concepts in ARIA

The term "real-time" is often used loosely to mean "fast." In engineering, it has a precise meaning: a real-time system is one with guaranteed response time bounds. Missing a deadline is not just slow — it is a system failure.

Hard vs. Soft Real-Time in ARIA

Hard Real-Time
Flame detection → relay activation.

Must complete within 2 seconds of detection. Fire spreads exponentially — each second of delay is potentially significant structural damage. The Arduino Uno's single-threaded loop guarantees this deadline is met with no preemption risk.
Soft Real-Time
Telegram alert delivery.

Should arrive within 60 seconds. A delayed notification is unfortunate but doesn't directly affect physical safety. This task runs asynchronously in a FreeRTOS task with lower priority than sensor polling.

FreeRTOS Dual-Core Division of Labour

The ESP32's two cores are explicitly assigned different priorities. Core 1 runs the main loop — sensor reading, threat analysis, Li-Fi transmission. Core 0 runs the Telegram task — network connection, JSON formatting, HTTPS requests. This physical separation means a slow or blocking Telegram API response cannot delay sensor polling. The two responsibilities literally cannot interfere with each other because they run on different hardware cores.

This is what the v4.0.4 Telegram queue fix was enabling: by buffering messages in a queue and processing them asynchronously on Core 0, the sensor loop on Core 1 is never blocked waiting for network I/O.

Priority Inversion Avoidance

Priority inversion is a subtle real-time bug where a low-priority task holds a resource that a high-priority task needs, causing the high-priority task to effectively run at low priority. ARIA avoids this by design: the Telegram task doesn't share any mutex or resource with the sensor loop. They communicate only through a fire-and-forget queue (the Telegram message queue), which uses atomic pointer operations — no mutex required, no inversion possible.

Design Patterns — Intuitive Explanations

Software engineers use "design patterns" as named solutions to recurring problems. ARIA implements several classic patterns, applied to embedded safety systems in ways worth understanding on their own terms.

The Producer-Consumer Pattern

The Telegram queue is a textbook producer-consumer implementation. The sensor loop (producer) generates alert messages and puts them into a bounded queue. The Telegram task (consumer) takes messages out and sends them. The queue acts as a buffer — if the producer generates alerts faster than the consumer can send them, messages wait in the queue rather than being lost or blocking the producer.

The key insight of v4.0.4 was that this pattern requires careful ownership semantics. When you "put a message in a queue," you're handing ownership of that memory to the consumer. Using plain pointers (C-strings allocated with strdup) makes ownership explicit and unambiguous — something C++ String objects obscure behind their destructor semantics.

The State Machine Pattern

Both units extensively use state machines. A state machine is a formal description of behaviour: the system is always in exactly one state, and can transition to other states only in response to defined events. This makes behaviour predictable and verifiable — no "undefined" states, no unexpected transitions.

The Li-Fi decoder's four states (WAIT_START → WAIT_DATA → READ_BITS → PROCESS) form a tight state machine where each state has a clear entry condition, a clear exit condition, and a timeout guard. Without the timeout guard, an incomplete frame could leave the state machine stuck in READ_BITS forever — a bug that would only manifest as "receiver stopped responding" with no visible error.

The Watchdog Pattern

Multiple watchdogs operate in ARIA at different timescales. The Li-Fi link watchdog operates at 15-second granularity. The safety watchdog operates at 10-second granularity. The Telegram heartbeat operates at 5-minute granularity. Each provides a different tier of assurance: is the physical link alive? Is the relay state consistent? Is the system still running and connected?

⏰
Watchdogs are like a check-in system for a solo hiker. You tell someone: "If you don't hear from me every hour, assume I'm in trouble and send help." The value isn't in the normal check-ins — it's in what happens when check-ins stop. ARIA's watchdogs embody the same logic: silence implies failure, and failure demands a safe response.

What Makes This "Production-Grade"?

Many projects work when everything goes well. Production-grade systems work when things go badly. The gap between the two is where most of ARIA's engineering effort was spent.

Version History as Evidence

ARIA's changelog isn't just a list of features — it's a map of discovered failure modes. v4.0.3 fixed Telegram HTTP errors. v4.0.4 fixed heap corruption from the FreeRTOS queue bug. v4.0.7 fixed the Li-Fi timing issue for specific bit patterns. Each version represents a discovered edge case that a naive implementation would simply ignore or label as "occasional instability."

Memory Management Discipline

The v4.0.4 fix demonstrates understanding of memory ownership — a concept that separates embedded programmers from systems engineers. The fix isn't just "use a different data type." It's a careful analysis of who owns each allocation, when it gets freed, and what happens if a free is missed or duplicated. ARIA adds explicit heap monitoring (logging free heap size every 30 seconds) to detect creeping memory leaks before they cause crashes.

Graceful Degradation at Every Layer

Production systems define and implement degraded-mode behaviour. ARIA's degraded modes are explicit and deliberate:

Full System
All four layers operational: on-site alerts + Li-Fi relay control + Telegram cloud notification + web dashboard.
No Internet
On-site alerts + Li-Fi relay control continue normally. Web dashboard offline, Telegram paused. Physical safety unaffected.
Li-Fi Link Lost
Receiver enters safe state (relay OFF). Transmitter continues on-site alerts + Telegram. Remote ventilation control lost; manual intervention required.
ESP32 Crashed
All ESP32 functions offline. On-site physical alerts (buzzer, LED) from before crash remain visible. Receiver times out safely. Manual inspection required.

The 60-Second Telegram Cooldown

A single threshold crossing can produce dozens of alerts in a minute as the sensor reading oscillates around the boundary. Without the cooldown, ARIA could send 60+ Telegram messages in one minute, exhausting the API rate limit, flooding the user's phone, and potentially causing the bot to be banned. The 60-second cooldown is an explicit acknowledgement that the human receiving the alert is part of the system, with their own cognitive bandwidth limits.

Key Engineering Insights

Synthesized Principles

1. Complexity is a liability in safety systems

The more complex your safety actuator, the more ways it can fail. The Arduino Uno's simplicity isn't a limitation — it's the feature. Reserve complexity for the parts of the system where it adds value (intelligence, connectivity, analysis) and keep the life-safety action path as short and simple as possible.

2. Every measurement is a comparison — calibrate the reference

A sensor reading without a reliable baseline is noise. ARIA's 3-minute calibration is not a delay — it is the process of establishing the ruler by which all future readings are measured. The quality of your baseline is the quality of your system.

3. Design for the failure, not the happy path

Any code path can be reached. ARIA's engineers asked "what if the queue is full? what if strdup fails? what if the link goes silent? what if the relay is ON but shouldn't be?" and coded answers to each. This habit of systematically imagining failures — and coding their responses before they occur — is what separates professional engineering from functional prototyping.

4. Protocol design must match channel physics

The v4.0.7 timing fix demonstrates that a protocol is only correct if it accounts for the actual physical behaviour of its channel. The channel physics (no gap between start pulse and first bit) invalidated a protocol assumption (falling edge marks transition). The fix required going back to first principles and deriving the timing from what is physically guaranteed — the rising edge — rather than what was assumed.

5. User trust is a system component

Alert fatigue — the phenomenon where users disable or ignore safety systems after too many false alarms — is a genuine failure mode. ARIA's environmental compensation, multi-sensor voting, and Telegram cooldown all exist to protect user trust. A system that generates one real alert per month and two false alarms is not 67% reliable — it is unreliable, because eventually the user will stop checking alerts. Reducing false positives from 40% to under 2% is the difference between a trusted safety system and an ignored noise-maker.

The goal of ARIA is not to demonstrate that we can connect sensors to a microcontroller. It is to demonstrate that we understand why systems fail, how those failures propagate, and what design choices prevent or contain them. That understanding — applied with discipline across every layer from sensor physics to memory management to protocol timing — is what makes an embedded system worthy of trust in a safety-critical role.
